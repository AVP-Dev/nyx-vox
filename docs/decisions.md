# Архитектурные решения (ADR)

> Фиксируем НЕОЧЕВИДНЫЕ решения — то, что новый агент/человек мог бы
> сделать иначе, не зная контекста. Не пиши сюда очевидные вещи.

## Формат записи
```
### [YYYY-MM-DD] Заголовок решения
Контекст: почему вообще встал вопрос
Решение: что выбрали
Альтернативы: что рассматривали и почему отвергли
Последствия: что это значит для будущей разработки
```

---

### [2024-01-01] Tauri 2 вместо Electron
Контекст: нужен десктопный фреймворк для приложения с нативным доступом к аудио и системным API.
Решение: Tauri 2 (Rust backend + WebView frontend).
Альтернативы: Electron — отклонён из-за большого размера бандла и высокого потребления памяти. Flutter — отклонён из-за сложности интеграции с macOS audio APIs.
Последствия: весь бэкенд на Rust, фронтенд в Tauri WebView, IPC через `invoke()`.

### [2024-01-01] Next.js static export вместо SSR
Контекст: фронтенд рендерится внутри Tauri WebView, нет серверной части.
Решение: Next.js с `output: 'export'` — полностью статический HTML/JS.
Альтернативы: Vite — рассматривался, но Next.js выбран для familiar DX. SSR — не нужен, т.к. нет сервера.
Последствия: нет API routes, нет SSR, всё через Tauri IPC.

### [2024-01-01] Три STT-движка с fallback
Контекст: нужен надёжный speech-to-text с fallback при недоступности облака.
Решение: три движка — Whisper (локальный), Deepgram (облачный), Groq (облачный). Runtime fallback между ними.
Альтернативы: только Whisper — отклонён из-за медленной локальной обработки. Только облако — отклонён из-за зависимости от интернета.
Последствия: `active_stt_mode` может отличаться от `stt_mode`, сложная логика переключения.

### [2024-01-01] AES-256-GCM для API-ключей
Контекст: API-ключей пользователей нужно хранить безопасно.
Решение: AES-256-GCM с nonce, привязанным к machine-id через machineid-rs.
Альтернативы: Keychain macOS — отклонён из-за сложности кроссплатформенного расширения. Plaintext — небезопасно.
Последствия: ключи теряются при смене hardware, но это приемлемо для desktop-приложения.

### [2024-01-01] Zustand + TanStack Query
Контекст: нужно разделить клиентский UI-стейт и серверное состояние.
Решение: Zustand для UI-стейта (processing, transcript), TanStack Query для серверного (AI-запросы, настройки).
Альтернативы: Redux — избыточен для такого объёма. Jotai — менее предсказуем для persist.
Последствия: настройки хранятся на бэкенде (tauri-plugin-store), фронтенд читает через invoke().

### [2024-01-01] Единый source of truth для галлюцинаций
Контекст: STT-движки генерируют артефакты (повторы, субтитры, служебные фразы). Раньше cleanup был и на фронте, и на бэке.
Решение: весь cleanup на бэкенде, фронтенд только отображает результат.
Альтернативы: cleanup на фронте — отклонён из-за дублирования и рассинхронизации.
Последствия: `utils.rs` — единственный файл с regex-паттернами очистки.

### [2024-01-01] Семафор для AI-запросов
Контекст: пользователь может быстро нажимать запись несколько раз, создавая множественные AI-запросы.
Решение: `AiSemaphore` (tokio::sync::Semaphore) ограничивает параллельные вызовы API.
Альтернативы: очередь запросов — сложнее в реализации. Без ограничений — risk rate limiting от API.
Последствия: дополнительный слой синхронизации в `lib.rs`.

### [2026-07-07] Toast + ConfirmDialog вместо alert/confirm
Контекст: в SettingsPanel.tsx и GeneralTab.tsx использовались нативные `alert()` и `confirm()` — некрасиво, нет контроля стиля, блокируют UI.
Решение: созданы `src/components/ui/Toast.tsx` (auto-dismiss 3с, success/error/info) и `src/components/ui/ConfirmDialog.tsx` (модалка с destructive-стилем). Хуки `useToast` и `useConfirm` для управления состоянием.
Альтернативы: react-hot-toast / sonner — отклонены из-за лишней зависимости для 10 вызовов. Глобальный Toast Context — избыточно, Toast передаётся через props между SettingsPanel и GeneralTab.
Последствия: все `alert()`/`confirm()` заменены на UI-компоненты. Новые диалоги должны использовать ConfirmDialog, уведомления — Toast.
